# Архитектура Linager

Статус: реализовано в 0.1; разделы 12a–12e описывают, что сделано и где реализация отошла от первоначального плана. Исходные требования: `docs/kickoff/PROMPT.md`, решения: `docs/decisions.md`, интерфейс: `docs/design/ui-spec.md`.

## 1. Общая схема

```
 браузер ──HTTP(S)──▶ Caddy/nginx ──HTTP──▶ linager server (админка, API, WS/SSE) ──▶ PostgreSQL (localhost)
                                                   ▲
 linager agent (root, Debian/Ubuntu) ──WSS + mTLS, исходящее──┘  (отдельный порт агентов)
```

- Один бинарник `linager`, подкоманды: `server`, `agent`, `install`, `update`, `backup`, `version`.
- Два независимых слушающих порта сервера, оба задаются при установке без значений по умолчанию:
  - **порт админки** — обычный HTTP. Предполагается обратный прокси (Caddy) на этом же или соседнем сервере; тот же режим для закрытых и локальных сетей;
  - **порт агентов** — собственный TLS сервера Linager (самоподписанный сертификат, отпечаток закрепляется на агенте) и mTLS после привязки.
- Агенты в 0.1 подключаются напрямую к порту агентов, а не через прокси: mTLS через обычный HTTP-прокси не пройдёт. См. открытый вопрос 1.

## 4. Протокол и привязка агента

### 4.1 Привязка (enrollment)
1. `linager install` в режиме «Клиент» спрашивает `host:port` сервера, генерирует ключ Ed25519 (`/etc/linager/agent.key`, 600) и выводит публичный ключ и **ключ привязки** `XXXX-XXXX`: первые 40 бит `SHA-256(pubkey)` в Base32 (Crockford).
2. Агент подключается к порту агентов по TLS. Отпечаток сервера проверяется флагом `--fingerprint`; без флага агент показывает отпечаток и просит явного подтверждения.
3. Агент отправляет запрос привязки: публичный ключ, имя хоста, адрес, версия ОС и агента, версия протокола. Сервер создаёт запись `pending` (срок жизни 15 минут, лимит запросов с одного адреса).
4. **Код сверки** (4–6 символов) = усечённый `HMAC(SHA-256(server_cert) ‖ agent_pubkey, nonce)`. Показывается на агенте и в админке рядом с отпечатком: при подмене сервера коды разойдутся.
5. Администратор в админке вводит ключ привязки с консоли агента (экран «Ждут подтверждения»). Сервер сравнивает его с ключом из публичного ключа в запросе. Несколько неудачных попыток блокируют запись.
6. Сервер выпускает агенту клиентский сертификат Ed25519 от внутреннего CA (срок 1 год, автообновление через канал) и отдаёт его вместе с сертификатом CA. Дальше только mTLS.

### 4.2 Рабочий канал
- WSS, исходящее соединение от агента, автопереподключение с экспоненциальной паузой и джиттером.
- Конверт сообщения: `v` (версия протокола), `id`, `seq`, `ts`, `type`, `payload`, `sig` (Ed25519 отправителя). Сервер подписывает команды отдельным ключом подписи команд, агент принимает только подписанные и свежие команды (защита от повторов по `seq` и `ts`).
- Версионирование: сервер хранит поддерживаемые версии протокола и работает с агентом предыдущей версии; версия ниже минимальной помечается «не поддерживается».
- Типы сообщений: `hello`, `metrics`, `cmd`, `cmd.result`, `stream.open/data/close` (терминал, логи), `update.*`, `ping`.
- Метрики шлются пачкой каждые 5 с; при потере связи агент буферизует до 1 часа (кольцевой буфер) и досылает при подключении.

### 4.3 Откат сети и файрвола
Выполняет агент и только он:
1. Черновик хранится на сервере, на агент ничего не уходит до «Применить».
2. «Применить»: агент делает копию текущей конфигурации, пишет журнал отката в `/var/lib/linager/pending/` (переживает перезапуск агента и перезагрузку), применяет правку (`nft -c` затем `nft -f`; для сети `ifup/ifdown` с резервной копией `interfaces`) и запускает таймер 30 секунд.
3. Подтверждение приходит по каналу; без него (или при потере связи) агент возвращает конфигурацию. Резервный механизм: одноразовый `systemd-run --on-active=35s linager agent rollback`, если процесс агента сам упал.
4. Подтверждённая конфигурация записывается в `/etc/nftables.conf` и в конфигурацию сети своего бэкенда: `/etc/network/interfaces` (ifupdown, Debian) или `/etc/netplan/*.yaml` (netplan, Ubuntu; применение через `netplan try`-подобную схему с собственным таймером агента). Бэкенд определяется агентом автоматически; интерфейсный слой `network.Backend` общий.
5. Предупреждения до применения вычисляет сервер по описанию правок (порт 22, основной интерфейс) и по адресу, с которого агент подключён.

## 5. База данных

PostgreSQL только локальный: доступ через unix-сокет или `127.0.0.1`, `scram-sha-256`, роль `linager` со случайным паролем. DSN в `/etc/linager/server.yaml` (600, владелец `linager`). Миграции применяются при старте сервера под блокировкой (`pg_advisory_lock`).

Основные таблицы (первая миграция — этап 1):

- `users`, `roles`, `user_roles` — пользователи и роли заложены сразу; на старте один пользователь с ролью `admin`. Поля: `password_hash` (argon2id), `totp_secret`, `totp_enabled`, `failed_attempts`, `locked_until`.
- `sessions` — id (хэш токена), `user_id`, IP, User-Agent, `expires_at`, CSRF-секрет.
- `servers` — идентификатор, имя, `agent_pubkey`, отпечаток сертификата, статус (`pending/approved/revoked`), версии ОС, агента, протокола, включённые модули, `last_seen`.
- `enrollments` — запросы привязки: pubkey, ключ привязки, код сверки, срок, число попыток.
- `dashboards`, `dashboard_items` — дашборд и порядок карточек (`position`), добавление и удаление только с дашборда.
- `commands` — очередь команд агентам: тип, параметры, статус, результат, срок, автор.
- `audit_log` — кто, что, где, когда, результат, IP. Пишется на каждое действие администратора.
- `releases`, `update_runs`, `update_steps` — кэш релизов и история обновлений.
- `settings` — ключ-значение (сроки хранения метрик, канал обновлений).
- Метрики: `metrics_raw` (5 с), `metrics_1m`, `metrics_5m`, `metrics_15m`, `metrics_1h`, `events` (перезагрузки, падения служб).

### Метрики
- Секционирование `PARTITION BY RANGE (ts)`: raw — часовые секции, 1m — дневные, 5m — недельные, 15m и 1h — месячные. Секции создаёт и удаляет планировщик сервера (`DROP` секции вместо `DELETE`).
- Агрегация в планировщике сервера (не `pg_cron`, не TimescaleDB): каждую минуту сворачивает raw → 1m, каждые 5 минут 1m → 5m и т. д.; для каждого окна хранит min, avg, p95, max. Агрегаты идемпотентны (`INSERT ... ON CONFLICT`).
- Сроки по умолчанию: 5 с — 1 час, 1 мин — 7 дней, 5 мин — 90 дней, 15 мин — 180 дней, 1 час — 360 дней; настраиваются в `settings`.
- API истории выбирает таблицу по периоду согласно таблице из `ui-spec.md`. Данные для offline-сервера доступны.
- Запись батчами (`COPY`/multi-row insert).

## 6. Сервер

- Модули: `auth` (логин, сессии, TOTP, блокировки, CSRF), `agents` (WS-хаб, маршрутизация команд), `api` (REST для вебa), `live` (SSE/WS-поток дашборда), `scheduler` (агрегация, очистка, кэш релизов), `updater` (раскатка), `audit`.
- Режим обратного прокси: `listen` (по умолчанию `0.0.0.0:<порт>`, порт задан при установке), `trusted_proxies` (по умолчанию `0.0.0.0/0, ::/0`: заголовки `X-Forwarded-For/Proto/Host` принимаются от любого, мастер этого не спрашивает; список можно сузить в `server.yaml`), `base_path` (по умолчанию пустой, правится в `server.yaml`), поддержка WebSocket-upgrade, `cookie_secure: auto` (по `X-Forwarded-Proto`; в закрытой сети по чистому HTTP cookie не помечается Secure, мастер предупреждает).
- Защита: ограничение попыток входа по IP и по пользователю с растущей задержкой, CSRF-токен на всех изменяющих запросах, строгие cookie (`HttpOnly`, `SameSite=Strict`), заголовки CSP, `X-Frame-Options`, проверка `Origin` на WebSocket.
- Служба работает от `linager`, `NoNewPrivileges`, `ProtectSystem=strict`, `ReadWritePaths` только для `/var/lib/linager`.

### Удаление клиента из админки
`DELETE /api/servers/{id}` с телом `{"name": "<имя сервера>", "uninstall": true|false}`; имя повторяется для подтверждения. Порядок:
1. Если `uninstall` и агент онлайн, сервер отправляет подписанную команду `agent.uninstall`; агент удаляет сертификат и состояние, отключает и останавливает службу, при `purge` стирает каталог данных и конфиг (бинарник остаётся: он может быть и сервером), и завершается с кодом 78 (systemd не перезапускает).
2. Строка `servers` удаляется; каскадом уходят элементы дашбордов и очередь команд. Метрики и события хранятся с привязкой к серверу и удаляются вместе с ним (этап 3). Записи журнала аудита остаются.
3. Соединение закрывается. Сертификат агента перестаёт работать сразу, потому что каждое подключение сверяется с таблицей `servers`: на отозванного агента сервер отвечает 401 с `X-Linager-Reason: revoked`, агент останавливается (код 78).
4. Если агент был офлайн или команда не дошла, запись всё равно удаляется; агент при следующем подключении получит `revoked` и остановится, а при желании хост очищается вручную `linager agent uninstall`.
5. Действие пишется в журнал аудита (`server.delete`: был ли онлайн, отправлена ли команда удаления).
Тот же хост можно привязать заново: после удаления он снова проходит привязку.

## 7. Агент

- Работает от root (нужен для nft, apt, systemd, PTY). Каждый модуль включается отдельно в `/etc/linager/agent.yaml`; выключенный модуль не регистрирует команд, сервер не показывает вкладку.
- Модули: `metrics`, `terminal`, `services`, `apt`, `processes`, `logs`, `files`, `network`, `firewall`, `docker`. Единый интерфейс `Module{Name, Start, Handle(cmd)}`.
- Опасные действия подтверждаются в админке; сервер дополнительно помечает их в команде, агент отказывает без метки.
- Служба `linager-agent.service` с `Restart=always`.

## 8. Установщик

### 8.1 `install.sh`
Тонкий скрипт (POSIX sh, около 80 строк):
1. Очищает экран и буфер прокрутки перед запуском (`printf '\033[H\033[2J\033[3J'`).
2. Проверяет Debian 12/13 или Ubuntu 22.04/24.04/26.04, amd64 или arm64 (64-разрядная система), root, наличие `curl`.
3. Скачивает релиз и `SHA256SUMS` с `SHA256SUMS.minisig`, проверяет сумму и подпись (минимальный `minisign` из репозитория Debian, публичный ключ вшит в скрипт).
4. Запускает `linager install "$@"`; без TTY сразу идёт в неинтерактивный режим.
Безопасный вариант в документации: скачать, прочитать, проверить подпись, запустить.

### 8.2 Мастер `linager install`
- Полноэкранный TUI на отдельном экране терминала (alternate screen): на экране только логотип, шаг и поле ввода, вывод команд не показывается.
- Шапка с логотипом и списком шагов (`✓` готово, `●` текущий, `○` впереди), внизу один прогресс-бар этапа и одна строка текущего действия. Минимум текста, без пояснений там, где вопрос ясен.
- Подробный вывод (apt, postgres) пишется в `/var/log/linager-install.log`; при ошибке мастер показывает 10 последних строк и путь к журналу, откат изменений установщика по возможности.
- Язык по `LANG` (ru/en), флаг `--lang`. Цветовая схема из макета (один акцент, зелёный/жёлтый/красный). Работает без цвета (`NO_COLOR`, не-TTY).
- Первый вопрос: **Клиент или Сервер**.

**Сервер.** Вопросы: порт агентов (обязательно), порт админки (обязательно), режим админки (Caddy на этом сервере или свой обратный прокси; для Caddy дополнительно домен), логин и пароль администратора (пароль скрыт, подтверждение, проверка длины).
Этапы с прогрессом: проверки (ОС, root, systemd, свободные порты) → PostgreSQL (`apt-get install`) → база и роль → конфигурация и ключи (CA, сертификат порта агентов, ключ подписи команд) → служба systemd → администратор → запуск и проверка.
Итог: адрес админки, отпечаток сертификата агентов, готовая команда для клиента, пример блока Caddy с подставленными адресом и портом, подсказка по nftables для порта агентов.

**Клиент.** Вопросы: `host:port` сервера (обязательно). Этапы: проверка связи → отпечаток сервера и подтверждение (или `--fingerprint`) → генерация ключа → запрос привязки. Экран ожидания показывает ключ `XXXX-XXXX`, код сверки и отпечаток, обновляется до подтверждения; затем служба `linager-agent` включается и запускается.

**Неинтерактивный режим:** `linager install server --agent-port N --admin-port N --admin-mode caddy|proxy [--domain D] --admin-user U --admin-password-file F` и `linager install agent --server HOST:PORT --fingerprint SHA256:...`. Без обязательных флагов команда завершается ошибкой с понятным сообщением, значений по умолчанию для портов нет.

## 9. Подпись и обновления

- **Подпись релизов: minisign-совместимая Ed25519.** Один вшитый публичный ключ, проверка на чистом Go без внешних зависимостей, `minisign` есть в репозитории Debian для проверки вручную. Cosign отклонён: тянет цепочку Sigstore и сетевые проверки, лишнее для закрытых сетей.
- Релиз: `linager_linux_amd64` и `linager_linux_arm64`, `.deb` для каждой архитектуры, `SHA256SUMS`, `SHA256SUMS.minisig`, `manifest.json` (версия, канал, минимальная версия агента, версия миграций, список изменений) с подписью.
- Секретный ключ подписи хранится в секрете GitHub Actions (`MINISIGN_KEY`); его создаёт владелец (инструкция будет в `docs/`).
- Сервер кэширует релизы с GitHub (`bolgov0zero/linager`), проверяет подпись и раздаёт агентам. Порядок: сервер, потом агенты.
- Обновление сервера: проверка подписи → `pg_dump` → остановка службы → резервная копия бинарника → атомарная замена (`rename`) → миграции вперёд → запуск → проверка здоровья → при неудаче автооткат бинарника (миграции вперёд не откатываются, поэтому `pg_dump` предварительный).
- Обновление агента: скачивание у сервера, проверка подписи, замена, перезапуск. Новый агент подтверждает работоспособность первым успешным подключением; если подтверждения нет, отдельный таймер (`systemd-run`, около 70 секунд: 60 на подключение плюс запас на перезапуск) возвращает `linager.prev`.
- Офлайн-агенты встают в очередь; порядок раскатки и «остановить при ошибке» реализует сервер.

## 10. Безопасность (сводка)

TLS на порту агентов, mTLS и подписанные сообщения; argon2id; TOTP; блокировка перебора; CSRF; журнал аудита всех действий; секреты 600; минимальные права службы сервера; подтверждение опасных действий; отпечаток и код сверки при привязке; CSP и строгие cookie.

## 11. CI и релизы

- GitHub Actions: `go vet`, `golangci-lint`, тесты (с PostgreSQL в сервис-контейнере), сборка фронтенда, `linux/amd64` и `linux/arm64` (тесты и на arm64-раннере), `.deb` (`nfpm`), `SHA256SUMS`, подпись, публикация в Releases по тегу `v*`.
- Тест установщика: матрица Debian 12/13 и Ubuntu 22.04/24.04/26.04 в контейнерах с systemd (неинтерактивный режим) плюс проверка TUI через снимки терминала.
- Версионирование: SemVer, каналы `stable` (теги `vX.Y.Z`) и `beta` (`vX.Y.Z-beta.N`).

## 12. План этапов 0–2

### Этап 0. Репозиторий и каркас
Состав: создать публичный репозиторий `bolgov0zero/linager` (Apache-2.0, `README`, `LICENSE`, `NOTICE`, `.gitignore`, `CLAUDE.md`, `docs/`); `go.mod`, `cmd/linager` с подкомандами-заглушками и `version`; Makefile; `golangci-lint`; CI (тесты, линтеры, сборка amd64); workflow релиза (сборка, `.deb`, суммы, подпись, Releases); `install.sh` с очисткой экрана и проверками; каркас `web/` (Vite + Svelte, шрифты Medeo и лицензия в репозитории, переключатель темы).
Готово, когда: CI зелёный, по тегу `v0.0.1` публикуется подписанный релиз, `linager version` работает на Debian 12/13 и Ubuntu 22.04/24.04/26.04, установка заглушки через `install.sh` проходит.

### Этап 1. БД, протокол, привязка, авторизация
Состав: миграции (раздел 5), слой доступа (sqlc), конфиг; `internal/pki` (CA, сертификаты, отпечатки, ключи привязки, коды сверки); `internal/protocol` (конверт, подпись, версии); порт агентов (TLS, mTLS, WS-хаб, переподключение); агент: hello, привязка, хранение ключа и сертификата; админка: вход (argon2id, сессии, CSRF, блокировки), TOTP, экран «Ждут подтверждения», аудит; тесты протокола и привязки (включая подмену отпечатка и неверный ключ).
Готово, когда: два процесса на одной машине проходят полную привязку и обмениваются подписанными `ping`; перебор ключа привязки блокируется; админ входит с TOTP; всё действие админа в `audit_log`.

### Этап 2. Установщик
Состав: `install.sh` в боевом виде; мастер `linager install` (раздел 8): сервер и клиент, неинтерактивный режим, журнал; установка PostgreSQL и роль со случайным паролем; конфиги 600; пользователь `linager`; службы systemd; режим обратного прокси (доверенные прокси, X-Forwarded, WebSocket, базовый путь), примеры Caddy и nginx в `docs/`; итоговый экран; тесты на чистых Debian 12 и 13 в контейнерах.
Готово, когда: на чистых Debian 12/13 и Ubuntu 22.04/24.04/26.04 за один прогон мастера поднимаются сервер и PostgreSQL, админка доступна через Caddy на соседнем контейнере, клиент привязывается и работает как служба; повторный запуск мастера не ломает установку (идемпотентность).

## 12a. Этап 3: метрики и дашборд (реализовано)
- Агент: сборщик по `/proc` каждые 5 с (CPU, RAM, диски, интерфейсы, нагрузка, uptime), раз в 30 с число упавших служб, раз в час число обновлений apt; нужна ли перезагрузка (`/var/run/reboot-required`). При обрыве связи до часа (720 образцов) буферизуются и досылаются пачкой (`metrics`, подписанное сообщение).
- Сервер: сырые данные в `metrics_raw` (часовые секции), свёртки `1m/5m/15m/1h` (суточные, недельные, месячные секции) считает планировщик раз в минуту (повторяемые вставки `ON CONFLICT`); устаревшие секции удаляются (`DROP`), сроки по умолчанию как в таблице политики. Свёртки старших уровней строятся из младших; p95 старших уровней приближённый (персентиль по p95 младшего уровня).
- API: `GET /api/dashboard`, `/api/dashboard/available`, `POST/DELETE /api/dashboard/items`, `PUT /api/dashboard/order`, `GET /api/servers/{id}`, `/metrics?period=`, `/metrics.csv`, `GET /api/live` (SSE: `metrics`, `status`, `dashboard`).
- События (перезагрузка, падение службы, подключение/отключение агента) пишутся в таблицу `events` и показываются на графиках.
- Последний полный образец и сведения о системе сохраняются в `servers`, поэтому после перезапуска сервера и для offline-серверов показываются последние значения.

## 12b. Этап 4: терминал, службы, apt, процессы, журналы (реализовано)
- Протокол: запрос-ответ (`cmd` / `cmd.result`) и потоки (`stream.open/data/input/resize/close`) поверх подписанного канала; сервер проверяет опасные действия и ставит флаг `dangerous` только после подтверждения администратора, агент без флага их отклоняет.
- Агент: модули включаются в `/etc/linager/agent.yaml` (`modules:`), список включённых модулей агент сообщает при подключении, вкладки отключённых модулей отвечают «модуль отключён». Перезагрузка доступна всегда.
- Имя сервера: при подключении берётся из hostname агента. Агент присылает hostname при каждом подключении (в том числе после перезагрузки) и проверяет его на каждом такте метрик; при изменении сразу отправляет сведения о системе. Сервер сохраняет новый hostname, и если имя сервера было получено из старого (`host` или `host-N`), оно меняется на новое (с суффиксом `-N` при совпадении). Переименование пишется в события сервера, дашборды перезагружают список.
- Терминал: PTY (`creack/pty`) с `bash -l` от root, до 5 сессий на агенте и 3 на сервер в админке (при превышении сервер принимает WebSocket и закрывает его с кодом 4029, который виден браузеру); открытие и закрытие сессии пишутся в аудит (объём данных, длительность), нажатия клавиш не пишутся.
- Службы: `systemctl` (не D-Bus: меньше зависимостей, тот же результат), имена юнитов проверяются; `stop/restart/disable` для `ssh`, `sshd`, `linager-agent` требуют подтверждения.
- apt: список обновлений из симуляции `apt-get -s upgrade --with-new-pkgs` (безопасность по источнику), установка и проверка идут потоком с живым логом, одна операция apt за раз. Вместе с текстом поток несёт события: строки `\x1e` + JSON (`queue`, `pkg`, `progress`). Агент запускает apt с `-o APT::Status-Fd=3`, читает `pmstatus`/`pmerror`/`dlstatus` с этого канала и сам ведёт состояние пакетов; события хранятся в задании отдельно от лога (лимит лога 1 МиБ их не обрезает) и проигрываются заново при подключении. Браузер вырезает строки событий из текста консоли.
- Процессы: топ по CPU или памяти из `/proc`, завершение процесса (SIGTERM/SIGKILL) с подтверждением; PID 1 и сам агент защищены.
- Журналы: `journalctl -f` потоком с фильтрами по юниту, ядру и приоритету.
- CSP админки: `style-src 'self' 'unsafe-inline'` (xterm.js вставляет стили во время работы); скрипты по-прежнему только `'self'`.

## 12c. Этап 5: файлы, сеть, файрвол, Docker (реализовано)
- Откат на агенте: `agent/pending.go`. Перед применением агент пишет журнал `/var/lib/linager-agent/pending.json`, запускает таймер 30 секунд и только потом меняет систему. Подтверждение делает изменение постоянным, без подтверждения (или при потере связи) агент откатывает сам. После перезапуска агента журнал разбирается заново: просроченное изменение откатывается сразу.
- Сеть (ifupdown, в том числе ifupdown2): агент строит кандидата `interfaces` рядом с оригиналом, переводит интерфейс (`ifdown -i старый`, `ifup -i кандидат`), оригинал `/etc/network/interfaces` не трогается до подтверждения; откат делает обратное. Правятся режим static/DHCP, адрес, шлюз, MTU, состояние; прочие опции стенцы (dns-*, hwaddress, скрипты) сохраняются. Интерфейсы из файлов `source` и виртуальные (docker, veth, wg) только для просмотра. **netplan (Ubuntu) в этой версии только для просмотра**: редактирование не включено, пока его нельзя проверить на живой системе.
- Файрвол: управляется только `table inet filter` (цепочки input, forward, output); чужие таблицы (Docker и др.) не меняются. Применение атомарное (`delete table` + новая таблица одним скриптом `nft -f`), правила проверяются `nft -c`; после подтверждения таблица записывается в `/etc/nftables.conf` с заменой только блока `table inet filter`. Предупреждения (закрытие порта 22, нет правила established, политика output drop) считает сервер.
- Черновики хранятся в БД панели (`drafts`), неподтверждённое изменение — в `pending_changes`; панель показывает счётчик, но таймер откатывает агент.
- Файлы: список, правка текстовых файлов до 1 МБ с проверкой изменений (по времени), создание, загрузка и скачивание потоком через канал агента, удаление с подтверждением; системные каталоги верхнего уровня удалять нельзя.
- Docker: Engine API через сокет, модуль включается только если сокет существует; контейнеры, образы, логи и pull потоком. На Docker и netplan на живых машинах не проверялось (нет в тестовой среде).

## 12d. Этап 6: обновления, бэкапы, журнал (реализовано)
- Подпись: minisign-совместимая Ed25519, проверка на чистом Go (`internal/release`, алгоритмы `Ed` и `ED`, проверка trusted comment); открытый ключ вшит (`release.PublicKey`, переопределяется ldflags). Манифест релиза (`manifest.json` + `.minisig`) содержит версию, канал, SHA-256 и размер (бинарника amd64, поля прежних релизов), карту `assets` (по архитектуре: имя, SHA-256 и размер бинарника `linager_linux_<arch>`), число миграций, `min_agent`, список изменений.
- Источник: GitHub Releases или зеркало (`update.source`); релизы скачиваются на сервер в кэш `/var/lib/linager/releases/<версия>/`, подпись и сумма перепроверяются перед каждой раздачей.
- Сервер: привилегированный `updater` (root) вызывается через systemd path-юнит по файлу запроса из админки; шаги verify, backup, stop, replace, migrate, start пишутся в `update-status.json`; при сбое бинарник возвращается. История в `update_runs`.
- Агенты: сервер раздаёт релиз по mTLS (`/v1/release/...`), команда `update.apply`, сообщения `update.event`; агент проверяет подпись, делает `linager.prev`, заменяет бинарник и взводит таймер отката (`systemd-run`, 70 с), новая версия подтверждает себя подключением. Менеджер раскатки (все сразу, по одному, сначала один; остановка при ошибке; очередь офлайн-агентов в `agent_updates`).
- Журнал аудита: `GET /api/audit` с фильтрами (префиксы действий через запятую, результат, пользователь, поиск) и страница «Журнал».
- Бэкапы: `linager backup` (pg_dump + конфигурация + ключи, права 600, ротация), ежедневный таймер, предобновленческая копия.
- Оповещения (Telegram, email) по решению владельца не реализуются.

## 12g. Вкладка «Безопасность» (0.1.42)
- Агент: модуль `security`, команда `security.state` без параметров (читает только фиксированные источники, внешнего ввода нет). Источники: `sshd -T` или `sshd_config`, `journalctl -t sshd -t sshd-session --since "7 days ago" -o short-unix` (потоковый разбор, не более 2 млн строк), запасной `/var/log/auth.log`, `fail2ban-client`, `/etc/apt/apt.conf.d`, `/etc/passwd` и `authorized_keys` (отпечатки считаются в Go), `loginctl`. Результат кэшируется на минуту.
- Завершение сессий: `POST /api/servers/{id}/security/terminate` (`session` или `user`, `confirm: true`), команда агента `security.terminate` требует флага подтверждения, берёт цели только из собственного списка удалённых сессий `loginctl` и пишет `security.session.terminate` в аудит.
- Сервер: `GET /api/servers/{id}/security`, прокси к агенту (таймаут 40 секунд). Вкладка скрыта, если агент не сообщил модуль `security`.

## 12i. Журнал файрвола (0.1.48)
- Метка правила: `log prefix "lg:<input|forward|output>:<id>:<A|D|R> "` с `limit rate 5/second`; `id` (первые 4 hex FNV-1a от текста правила без части журнала, счётчика и пробелов) считает панель (`fw-view.ts`), поэтому правило можно найти по метке, пока его текст не менялся. Агент метку не создаёт и правила не меняет: это обычный текст правила в черновике.
- Агент: `firewall.log` читает `journalctl -k -o short-unix --since "7 days ago"`, берёт строки с `lg:` (`parseFwLogLine`), отбрасывает старше 7 дней, отдаёт до 6000 новейших и `total`; кэш 15 секунд. Сервер: `GET /api/servers/{id}/firewall/log` (прокси). Фильтры, группировка и экспорт работают в браузере.

## 12j. Роли: оператор и аудитор (0.1.50)
- Миграция `00008`: роли `operator` и `auditor` в `roles`, таблицы `user_servers`, `user_groups`, `user_modules` (каскадное удаление). Одна роль на пользователя (`user_roles`), прежние пользователи остаются администраторами.
- Права: `server/access.go`. Каждый маршрут регистрируется через `Admin.route(mux, pattern, spec, handler)`; правило `spec`: `any`, `admin`, `srv` (любая роль, сервер доступен), `srv:<модуль>` (администратор, оператор с модулем), `srv:admin`, `mod:<модуль>`. Роль и права читаются из БД на каждый запрос (`Store.RoleOf`, `ServerAllowed`, `ModuleAllowed`), поэтому изменения действуют сразу. Недоступный сервер даёт 404, закрытый модуль 403. Потоки (`/stream`) проверяют модуль по виду потока (`streamModule`). Тест `TestRouteTableIsComplete` проверяет, что у каждого маршрута есть правило и что открытые для всех ролей маршруты перечислены явно.
- Фильтрация: список серверов, дашборд (для оператора и аудитора это ровно доступные серверы, `Store.DashboardSync`) и поток `/api/live` (события `metrics` и `status` несут `server_id`, `Live.PublishServer`) показывают только доступные серверы. Доступ по группе считается в `Store.AllowedServerIDs`.
- API: `POST /api/users` принимает `role`, `servers`, `groups`, `modules`; `PUT /api/users/{id}/access` меняет роль и доступ; `GET /api/me` отдаёт `role` и `modules`; `GET /api/servers` отдаёт `group_id`. Аудит: `user.create`, `user.access`.
- Веб: в «Настройки → Пользователи» выбор роли и кнопки «Серверы» (серверы по группам, переключатель группы включает все её серверы) и «Модули» (опасные помечены). Оператор и аудитор вместо «Настройки» видят «Профиль»; вкладки закрытых модулей, кнопки удаления, перезагрузки, привязки агента и редактирования дашборда скрыты.

## 12e. Доработки после проверки 0.1
- Сертификат агента продлевается по каналу (`cert.renew` / `cert.renewed`), когда остаётся меньше трети срока;
  агент перечитывает сертификат перед каждым подключением. Пауза переподключения сбрасывается после сессии дольше 30 секунд.
- Резервный откат сети и файрвола (раздел 4.3, пункт 3) реализован: одноразовый таймер `linager-agent-change-rollback`
  запускает `linager agent rollback-change` через 35 секунд и забирает журнал, если агент не справился сам.
- Операции apt не привязаны к потоку: обрыв связи не останавливает `apt-get`, повторный поток подключается к идущей операции и получает все события и лог с начала.
- Предупреждение о закрытии SSH считается по портам из `sshd -T` (агент отдаёт их в `firewall.state`).
- Обновление сервера: проверенный бинарник копируется в каталог только для root (`/var/lib/linager-updater`), контрольная сумма
  сверяется перед установкой; при сбое после миграций база восстанавливается из предобновленческой копии; понижение версии
  запрещено (сервер и агент); канал stable не принимает версии с суффиксом. Команда `linager restore`.
- Раскатка агентов хранит состояние в `settings` (`updates.rollout`) и продолжается после перезапуска сервера;
  сбой первого агента в режиме «сначала один» больше не подвешивает раскатку.
- `install.sh` при запуске через канал (`curl … | sh`) возвращает мастеру терминал.
- Интерфейс: форма точки `ELSH 40` у крупных заголовков, кнопка «Терминал» на карточках (адрес `#srv-<имя>/<вкладка>`),
  метки и баннер обновления агента, вкладки отключённых модулей скрыты.

## 13. Решения и открытые вопросы

Решено владельцем:
- Агенты подключаются на отдельный порт напрямую, не через прокси. За Caddy публичный порт админки 443; порт самого Linager для админки задаётся при установке (обязательно, без значения по умолчанию).
- Платформы: Debian 12/13 и Ubuntu 22.04/24.04/26.04 LTS. Установщик единый для семейства apt/systemd.
- Тестовая среда: две машины в локальной сети владельца (доступ предоставит владелец) плюс контейнеры в CI.
- Ключ подписи релизов создаёт владелец, секрет `MINISIGN_KEY`.
- Фронтенд: Svelte 5 + Vite (мой выбор, это только внутренний инструмент сборки веб-интерфейса).

Также решено:
- Режимы админки в мастере: (1) **Caddy** — установщик ставит Caddy на этот же сервер, сертификат Let's Encrypt для указанного домена, публичный порт 443; (2) **Обратный прокси** — установщик ничего не ставит и не настраивает, только запрашивает порты, адрес прослушивания, доверенные прокси и базовый путь (пример конфигов в `docs/`).
- Ubuntu 22.04, 24.04 и 26.04 LTS. При активном `ufw` вкладка «Файрвол» показывает предупреждение, остальное в 0.1 не делаем.

Открыто:
1. Let's Encrypt требует, чтобы домен указывал на сервер и порты 80/443 были доступны из интернета. В закрытой сети это не сработает; мастер проверит доступность и предложит режим «Обратный прокси». Тестовые машины в локальной сети проверят режим «Обратный прокси» и «Caddy» с тестовым центром сертификации (staging) или без сертификата.
2. Доступ к тестовым машинам по SSH-ключу (см. переписку); пароли в репозиторий и документы не попадают.
