# Безопасность Linager

## Модель угроз
Сервер Linager управляет серверами с правами root, поэтому компрометация панели равна компрометации всех клиентов. Защита построена в расчёте на то, что админка может стоять в локальной сети без HTTPS, а канал агентов может идти через недоверенную сеть.

## Что защищено и как
- **Канал агентов:** TLS 1.3, сертификат порта клиентов самоподписанный, агент закрепляет его отпечаток. После привязки взаимный TLS (mTLS) с сертификатом от внутреннего CA сервера (срок 1 год, агент продлевает его сам по каналу). Каждое сообщение подписано Ed25519 (ключ агента и отдельный ключ подписи команд сервера), есть счётчик последовательности и окно по времени против повторов.
- **Привязка клиента:** клиент проверяет отпечаток сервера (флаг `--fingerprint` или явное подтверждение), оба конца показывают **код сверки**, администратор вводит **ключ привязки** с консоли клиента. Пять неверных ключей отклоняют запрос; запросы ограничены по частоте и сроку (15 минут).
- **Вход администратора:** пароли argon2id, блокировка перебора (по IP и по логину с нарастающей паузой), одноразовые коды TOTP не принимаются повторно, сессии в БД (хранится хэш токена), cookie `HttpOnly`, `SameSite=Strict`, `Secure` при HTTPS, защита от CSRF токеном на каждом изменяющем запросе, проверка `Origin` у WebSocket.
- **2FA:** TOTP включается в админке («2FA»). Параметр `admin.require_totp: true` в `server.yaml` закрывает весь интерфейс, пока администратор не включит 2FA. Вход в два шага: сначала логин и пароль, и только если у пользователя включена 2FA, страница просит код. Верный пароль без кода сессию не создаёт и не считается неудачной попыткой; неверный код считается.
- **Коды восстановления:** при включении 2FA выдаются 10 одноразовых кодов (хранятся только хэши, показываются один раз). Код восстановления вводится вместо кода из приложения и сгорает; сгенерировать новые можно в «Настройки → Профиль» (нужен пароль), старые при этом аннулируются.
- **Passkey (WebAuthn):** отдельный способ входа кнопкой «Passkey» на странице входа, без логина и пароля. Ключ запрашивает проверку пользователя (PIN или биометрия), поэтому отдельная 2FA не нужна. Работает только по HTTPS (или на `http://localhost`) с доменным именем; идентификатор стороны равен имени хоста, с которым открыта панель, так что при смене домена ключи нужно добавить заново. Каждый вызов ограничен по частоте, challenge одноразовый и живёт 5 минут, источник запроса проверяется.
- **Завершение SSH-сессий:** на вкладке «Безопасность» администратор может завершить удалённую сессию или все сессии пользователя. Действие подтверждается, агент завершает только сессии из собственного списка (`loginctl terminate-session`), запись попадает в журнал аудита вместе с пользователем и адресом.
- **fail2ban, ключи и очистка диска:** установка и настройка fail2ban, бан и разбан адресов, удаление ключа из `authorized_keys` и очистка диска требуют подтверждения на сервере (`confirm`) и флага подтверждения на агенте, пишутся в журнал аудита. Адрес администратора, loopback и адреса из списка исключений заблокировать нельзя. Агент принимает только имена и адреса, которые проверил сам: файл `authorized_keys` берётся из его собственного списка для пользователя, цели очистки определяет он, а не браузер; перед удалением ключа сохраняется копия файла. Файлы fail2ban администратора не переписываются, настройка панели лежит в `/etc/fail2ban/jail.d/linager.conf`.
- **Роли.** Администратор имеет полный доступ. Оператор работает только на серверах и с модулями, которые выдал администратор (серверы выбираются по одному или целой группой: сервер, добавленный в группу позже, доступен сразу). Модуль закрывается целиком, на всех серверах оператора. Оператор не меняет настройки панели (пользователи, обновления, журнал аудита, сниппеты, группы), не добавляет и не удаляет агентов и не перезагружает серверы. Аудитор только смотрит дашборд, обзор и метрики выбранных серверов и ничего не меняет. Обоим доступен свой профиль (пароль, 2FA, passkey). Права проверяет сервер на каждом запросе (в браузере кнопки только скрываются): у каждого маршрута есть правило доступа, тест следит, чтобы новый маршрут не остался без него. Сервер, к которому у пользователя нет доступа, для него не существует (404); закрытый модуль даёт 403. Изменённые права действуют сразу, без нового входа. Администратор не может сменить роль себе и понизить последнего администратора; создание пользователя и смена его роли или доступа пишутся в журнал аудита. Модули «Терминал», «Файлы», «Сеть», «Файрвол», «Безопасность» и «Docker» дают доступ уровня root на хосте: оператор с терминалом может удалить агента или добавить свой ключ, поэтому панель помечает их предупреждением и по умолчанию они выключены.
- **Пользователи:** можно добавлять пользователей, менять свой пароль (остальные сессии завершаются), сбрасывать пароль и 2FA другим. Удалить самого себя нельзя. Все эти действия пишутся в журнал аудита.
- **Частота входа:** `admin.login_rate` в `server.yaml` (попыток в минуту с одного адреса, по умолчанию 10).
- **Заголовки:** строгая политика CSP (скрипты только свои; стили `'unsafe-inline'` нужны терминалу xterm.js), `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, `Permissions-Policy`, COOP и CORP, HSTS при HTTPS.
- **Опасные действия:** остановка `ssh` и `linager-agent`, перезагрузка, удаление файлов, завершение процессов, правила файрвола и сети, обновления требуют явного подтверждения; сервер ставит флаг подтверждения только после ответа администратора, агент без флага такие команды отклоняет.
- **Откат:** сеть и файрвол применяются с таймером 30 секунд на агенте; без подтверждения (в том числе при потере связи) настройки откатываются сами, журнал изменения переживает перезапуск агента.
- **Журнал аудита:** все действия администратора (вход, привязка, команды, правки, обновления, открытие и закрытие терминала с объёмом данных) записываются с адресом соединения и адресом из `X-Forwarded-For`. Нажатия клавиш в терминале не записываются.
- **Обновления:** релизы подписаны (minisign, Ed25519), открытый ключ вшит в бинарник; манифест, контрольная сумма и подпись проверяются на сервере и на агенте до замены; перед обновлением делается копия БД; при неудаче бинарник возвращается.
- **Права:** секреты (`server.yaml`, ключи, резервные копии) с правами 600; служба сервера работает от пользователя `linager` с ограничениями systemd (`ProtectSystem=strict`, `NoNewPrivileges`, фильтры адресных семейств, пустой набор capabilities кроме привязки портов); привилегированные операции (обновление) выполняет отдельная служба.
- **База данных:** только локальный PostgreSQL, `scram-sha-256`, случайный пароль роли; установщик отказывается продолжать, если PostgreSQL слушает не только localhost или допускает trust/md5 по TCP.

## Что нужно сделать администратору
1. **Включите 2FA** и по возможности `admin.require_totp: true`.
2. Если админка доступна по обычному HTTP в закрытой сети, **ограничьте порт админки файрволом**: по умолчанию сервер доверяет заголовкам `X-Forwarded-*` от любого адреса (`admin.trusted_proxies: 0.0.0.0/0`), и адрес клиента в журнале можно подделать при прямом доступе к порту. Для публичных установок сузьте `admin.trusted_proxies` до адреса вашего прокси и `admin.listen` до его сети.
3. Открывайте порт клиентов (`agents.listen`) только для нужных сетей.
4. Храните резервные копии как секреты: в них есть ключи CA.
5. Отключайте ненужные модули агента в `/etc/linager/agent.yaml` (терминал и файлы дают root-доступ ко всему хосту).

## Известные ограничения версии 0.1
- Все пользователи имеют одну роль «администратор» с полным доступом (включая терминал и файлы от root); отдельных ролей вроде «наблюдатель» пока нет, схема данных под них готова.
- Терминал и файловый менеджер работают от root агента.
- Редактирование сети на Ubuntu (netplan) отключено: только просмотр.
- Режимы TLS «Let's Encrypt/свой сертификат» для админки без Caddy не реализованы; используйте Caddy или свой обратный прокси.
