# Обновления, резервные копии и откат

## Как устроены релизы
Каждый релиз на GitHub содержит бинарник `linager_linux_amd64`, `.deb`, `SHA256SUMS` и подписанный `manifest.json` (версия, канал, контрольная сумма, число миграций БД, минимальная версия агента, список изменений). Подпись minisign (Ed25519) проверяется открытым ключом, **вшитым в бинарник**. Бинарник, не совпавший с подписанным манифестом, не устанавливается ни на сервере, ни на агенте.

## Обновление сервера
Из админки: страница «Обновления» (кнопка в шапке со счётчиком), «Обновить до X». С терминала:

```bash
sudo linager update --check      # что доступно
sudo linager update              # обновить (спросит подтверждение, --yes чтобы не спрашивать)
```

Порядок (виден в админке по шагам): проверка подписи → резервная копия (`pg_dump` + конфигурация и ключи) → остановка службы → замена бинарника (предыдущий хранится в `/var/lib/linager/prev/`) → миграции БД (только вперёд) → запуск и проверка (админка отвечает 200, порт клиентов принимает соединения, до 60 с). **Если проверка не прошла, предыдущий бинарник возвращается автоматически.** Миграции откатить нельзя, поэтому перед каждым обновлением делается копия БД: `/var/backups/linager/linager-pre-update-*.tar.gz`.

Из админки обновление запускает служба `linager-updater` (systemd path-юнит следит за файлом запроса и запускает `linager update --apply-request` от root): сама служба сервера работает без прав root и заменить бинарник не может. Установщик создаёт эти юниты.

## Обновление агентов
Агенты берут релиз **с сервера** (порт клиентов, mTLS), поэтому сначала обновляется сервер. На странице «Обновления» можно обновить одного, выбранных или всех; порядок: все сразу, по одному, сначала один и потом остальные; опция «остановить при ошибке». Офлайн-агент встаёт в очередь и обновляется при подключении. Агент старше минимальной поддерживаемой версии помечается «не поддерживается».

Агент проверяет подпись и контрольную сумму, сохраняет прежний бинарник (`/var/lib/linager-agent/linager.prev`), заменяет `/usr/local/bin/linager`, запускает **таймер отката** (`systemd-run`, исполняет прежний бинарник) и перезапускается. Новая версия подтверждает себя первым успешным подключением к серверу и отменяет таймер. **Если подключения нет, через ~70 с прежний бинарник возвращается автоматически.** Вручную на хосте клиента: `sudo linager agent update`, `linager agent status`.

## Каналы и источник релизов
Канал `stable` (теги `vX.Y.Z`) или `beta` (`vX.Y.Z-beta.N`) выбирается в админке. В `/etc/linager/server.yaml`:

```yaml
update:
  source: ""            # пусто = GitHub bolgov0zero/linager; "owner/repo"; либо URL зеркала с releases.json
  channel: stable
```

Зеркало (для закрытых сетей): каталог с файлами релизов и `releases.json` в формате GitHub API (`tag_name`, `prerelease`, `body`, `assets[].name/browser_download_url`), отданный по HTTP(S).

## Резервные копии
```bash
sudo linager backup --keep 7     # /var/backups/linager/linager-backup-<дата>.tar.gz (права 600)
```
В архиве: `db.dump` (pg_dump, формат custom), `config/server.yaml`, `data/` (ключи CA, сертификат и ключ подписи команд). **Архив содержит секреты, храните его так же бережно, как сервер.** Установщик включает ежедневную копию в 02:00 (`linager-backup.timer`, хранятся 7 последних).

Восстановление базы вручную:
```bash
sudo systemctl stop linager-server
tar -xzf linager-backup-XXXX.tar.gz db.dump
sudo -u postgres pg_restore --clean --if-exists --no-owner -d linager db.dump
sudo systemctl start linager-server
```

## Ключ подписи (для владельца репозитория)
Ключ создаётся один раз: `minisign -G -W -p minisign.pub -s minisign.key`. Содержимое `minisign.key` кладётся в секрет репозитория `MINISIGN_KEY` (при защите паролем ещё `MINISIGN_PASSWORD`), строка из `minisign.pub` вписывается в `internal/release/release.go` (`PublicKey`) и `install.sh` (`PUBKEY`). Релиз без секрета публикуется как pre-release без подписи, такие релизы установщик и обновление отвергают.
