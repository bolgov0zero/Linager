# Решения по проекту Linager

## Принятые решения
| Тема | Решение |
|---|---|
| Название | Linager |
| Язык и сборка | Go, один бинарник `linager` с ролями server и agent |
| Платформа | Debian 12 и 13, Ubuntu 22.04, 24.04 и 26.04 LTS (Debian 11 снят с поддержки), только amd64 |
| Репозиторий | GitHub, публичный, лицензия Apache-2.0 (допущение, можно сменить) |
| Установка | Скрипт `install.sh` скачивается с GitHub, мастер сразу спрашивает Клиент или Сервер |
| БД | Только локальный PostgreSQL, ставит и настраивает установщик, внешняя БД не поддерживается |
| Администраторы | Один администратор на старте, позже роли и пользователи |
| TLS и доступ | Самоподписанный, Let's Encrypt, свой сертификат, обратный прокси на этом же или соседнем сервере |
| Обновления агентов | Через сервер Linager (сервер кэширует релизы с GitHub), не напрямую |
| Обновления сервера | CLI и админка, с бэкапом БД, миграциями и автооткатом |
| Хранение метрик | 5 с: 1 час; 1 мин: 7 дней; 5 мин: 90 дней; 15 мин: 180 дней; 1 час: 360 дней (последние два уровня выбраны по просьбе «ещё 180 и 360», шаг агрегации предложен) |
| Языки интерфейса | Русский (основной) и английский |
| Шрифт | Medeo: Mono для текста, Pixel для заголовков и подписей, лицензия SIL OFL 1.1 |

## Как работает привязка клиента
1. На клиенте: адрес сервера, генерация ключа Ed25519, вывод ключа и отпечатка.
2. В админке появляется подключение в статусе «ожидает подтверждения».
3. Админ вводит ключ, подтверждает. После этого связь по mTLS, подписанные сообщения.
4. Дополнение к исходной идее: агент проверяет отпечаток сервера, показывается короткий код сверки на обеих сторонах.

## Подтверждено владельцем (14 ноября 2026)
- Debian 12 и 13 (11 не поддерживается). Лицензия Apache-2.0. Шаги агрегации 15 минут (180 дней) и 1 час (360 дней).
- Версия агента в списках показывается рядом с версией Debian.
- Владелец репозитория: GitHub `bolgov0zero`, репозиторий `bolgov0zero/linager` (заглушка `OWNER` заменена).
- Порты Linager (агентов и админки): значений по умолчанию нет, мастер спрашивает их обязательно; в неинтерактивном режиме флаги обязательны. Клиенты подключаются на отдельный порт напрямую, не через прокси. Публичный порт админки за Caddy: 443 (порт самого прокси).
- Поддержка Ubuntu 22.04, 24.04 и 26.04 LTS добавлена (14 ноября 2026). Установщик универсальный для семейства Debian/Ubuntu. Сеть на Ubuntu управляется через netplan, на Debian через ifupdown (бэкенды сети).
- Режимы админки в мастере: (1) «Caddy»: установщик ставит Caddy на этот же сервер, сертификат Let's Encrypt для домена, порт 443; (2) «Обратный прокси»: установщик ничего не ставит и не настраивает, только запрашивает порты. Адрес прослушивания `0.0.0.0` и доверенные прокси `0.0.0.0/0` заданы по умолчанию и не спрашиваются (по решению владельца); в `server.yaml` их можно сузить. Режим подходит и для закрытых сетей со своим прокси.
- Конфликт ufw и nftables на Ubuntu: в 0.1 только предупреждение во вкладке «Файрвол».
- Тестовая среда: две машины в локальной сети владельца, плюс контейнеры в CI.
- Ключ подписи релизов создаёт владелец, секрет `MINISIGN_KEY`.
- Подпись релизов: на усмотрение исполнителя, см. `docs/architecture.md` (minisign-совместимая Ed25519).
- TLS в первых релизах: только режим обратного прокси (без сертификата на стороне админки), Caddy как основной пример. Тот же режим для локальных и закрытых корпоративных сетей.
- Оповещения (Telegram, email) в первую версию не входят.
- Установщик: красивый, интерактивный, пошаговый, с прогрессом по этапам, без лишнего вывода; экран очищается перед запуском.

## Что не входит в первую версию
- Архитектура arm64.
- Внешний PostgreSQL.
- Несколько пользователей и роли (заложить в модель данных, реализовать позже).
- Оповещения.
- Режимы TLS «самоподписанный», «Let's Encrypt», «свой сертификат» для админки (заложить в конфиг, реализовать позже).
